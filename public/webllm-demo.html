How WebLLM Runs In A Browser

WebLLM lets a web page run a language model locally. The browser downloads model artifacts, caches them, prepares an MLC runtime, sends compute work through WebGPU, and streams tokens back to the user interface.

Big Picture: What WebLLM Is

WebLLM is a JavaScript library that lets a browser load and run supported LLMs locally using WebGPU acceleration.

  • Runs inside the browser instead of a backend server.
  • Uses WebGPU to access client-side GPU acceleration.
  • Downloads model files and caches them in browser storage.
  • Keeps prompts local unless the app explicitly sends them elsewhere.
  • Depends on browser support, GPU capability, memory, and model size.

Why Use WebLLM

WebLLM is useful when a browser can handle the workload locally and the application benefits from lower server dependency, privacy, responsiveness, or offline-friendly behavior.

  • No model-serving cluster is needed for supported client-side tasks.
  • Inference cost can move from server infrastructure to the user's device.
  • Prompts can stay local, which can improve privacy for suitable use cases.
  • Small tasks can feel fast because there is no server round trip after load.
  • A hybrid design can fall back to server inference when client capability is missing.

MLC Workflow

MLC LLM describes three major phases: download pre-quantized weights, compile/prepare a model library, and run the chat runtime.

  • Pre-quantized weights reduce size and make local execution practical.
  • Model compilation creates backend-specific execution code.
  • The runtime combines weights plus model library to generate tokens.
  • Downloaded and compiled artifacts can be cached for later runs.

WebGPU

WebGPU is the browser API that lets JavaScript submit structured GPU work. WebLLM uses it to run model math on the client machine instead of relying only on CPU execution.

  • Creates a GPU adapter and device for the page.
  • Allocates GPU buffers for input data, outputs, and intermediate work.
  • Runs compute shaders that perform parallel math.
  • Submits commands through a GPU queue controlled by the browser.
  • Maps to Metal, Direct3D, or Vulkan under the browser, depending on OS and browser.

WebGL vs WebGPU

WebGL made GPU graphics possible in the browser. WebGPU is the newer browser API designed for modern GPU workloads, including compute-heavy use cases like local LLM inference.

Area WebGL WebGPU
Primary design Built mainly for rendering graphics in the browser. Built for modern graphics and general GPU compute.
Programming model Older OpenGL-style state machine. More explicit device, buffer, pipeline, and command model.
Compute support Compute is indirect and awkward for AI-style workloads. Compute shaders are first-class, which fits tensor and matrix math better.
Browser-to-GPU path Maps to older graphics stacks and compatibility layers. Maps well to Metal, Direct3D 12, and Vulkan-style modern APIs.
Fit for WebLLM Useful historically, but not the right target for browser LLM inference. The preferred path for WebLLM because it can submit structured GPU compute work.
Simple takeaway Great for drawing graphics. Better for running serious parallel computation in the browser.

GPU / VRAM

The GPU performs the heavy parallel math. VRAM is the memory the GPU uses for model weights, runtime buffers, and token-generation state while inference is active.

Term Simple Meaning What Gets Allocated
VRAM Dedicated memory on many discrete GPUs. Model weights, input/output buffers, temporary tensors, and KV cache.
Unified memory Shared CPU/GPU memory used by systems like Apple Silicon. The GPU uses part of the shared memory pool for the same model runtime data.
Model weights The learned numbers that define the model. Large fixed buffers loaded so each token can use the model's parameters.
Activations Intermediate results produced inside transformer layers. Temporary working buffers used while each prompt/token is processed.
KV cache Stored key/value tensors from previous tokens in attention. Conversation context memory that grows with prompt and response length.
Logits/output buffers Scores for possible next tokens. Small output data used to select the next token before streaming it back.

In simple terms: browser storage keeps model files between sessions; VRAM or unified memory holds the active model and working data while the model is running.

IndexedDB / Cache

Browser storage keeps downloaded model artifacts on the user's machine, so repeat visits do not need to download the same large files again.

Storage Piece What It Does Why It Matters For WebLLM
IndexedDB Browser database for larger structured and binary data. Can hold model artifacts or cache metadata for this site origin.
Cache API Browser cache for request/response-style resources. Can store downloaded files so later loads avoid a full network fetch.
Site origin Storage is scoped to the page's domain/origin. Each app gets its own storage boundary in the browser profile.
Persistence Data remains after refresh and browser restart. Model files can remain local until the user clears site data.
Not VRAM Storage is disk/browser-profile data, not active GPU memory. The model still needs to load into runtime/GPU memory before inference.

First Load vs Second Load

First load is heavy because model artifacts are not yet on the machine. Later loads can reuse browser storage.

  • First load downloads model files and stores them locally.
  • Second load can read those files from cache/IndexedDB.
  • Both paths still need to initialize the runtime and GPU buffers.
  • GPU memory is temporary; browser cache is persistent.

What Happens When You Send A Prompt

An LLM response is generated one token at a time. WebGPU is mainly accelerating repeated matrix math.

  • Text is converted into token IDs.
  • Model weights and tokens are used in transformer layers.
  • The GPU produces scores for the next token.
  • The selected token is appended and the loop repeats.
  • KV cache keeps conversation context efficient during generation.

Why This Matters For Banking

Client-side LLMs give banks a practical way to bring AI closer to employees and customers while improving privacy, response time, and infrastructure efficiency for the right workloads.

  • Privacy by design: prompts can stay on the user's device for suitable workflows.
  • Faster experiences: local inference removes server round trips after the model is loaded.
  • Lower infrastructure cost: supported tasks can run without dedicated GPU serving clusters.
  • Stronger field enablement: useful for branch, contact-center, staff-assist, and offline-friendly workflows.
  • Flexible architecture: client-side inference can pair with server-side fallback for higher-scale or policy-sensitive flows.

Deployment Considerations

A strong production design can use WebLLM where it fits best and route heavier, unsupported, or tightly governed flows to server-side services.

  • Browser readiness: use capability checks to confirm WebGPU support before enabling local inference.
  • Model sizing: choose models that fit the device's GPU or unified memory profile.
  • Download experience: plan first-load messaging and caching for large model artifacts.
  • Observability: track app-level timings and lifecycle states while relying on platform tools for deeper GPU telemetry.
  • Model strategy: combine compact local models with stronger server models when task complexity requires it.
  • Governance: keep regulated decisions inside controlled, auditable, policy-approved workflows.

Browser GPU Learning Lab

WebGPU From JavaScript To GPU

Run small WebGPU programs, inspect what JavaScript can ask from the browser, then try IndexedDB examples that mirror how a browser app can keep large artifacts locally.

Simple Flow

JavaScript does not talk directly to Metal, Direct3D, or Vulkan. It calls WebGPU. The browser validates the work and maps it to the operating system's GPU stack.

HTML button JavaScript navigator.gpu WebGPU device and queue Metal / Direct3D / Vulkan GPU hardware

GPU Interaction Demos

Step 1

Check WebGPU availability

Feature check 
if (!navigator.gpu) {
  throw new Error("WebGPU is not available");
}

This checks whether the browser exposes the WebGPU API on this machine right now. It does not load a model or allocate GPU memory.

Step 2

Request GPU adapter

GPU choice 
const adapter = await navigator.gpu.requestAdapter({
  powerPreference: "high-performance",
});

The adapter represents the GPU option selected by the browser. Some hardware details may be hidden to reduce fingerprinting. 

Output will appear here.

Step 3

Request GPU device

Connection 
const device = await adapter.requestDevice();
console.log(device.limits);

The device is this page's active connection to the GPU. Device limits tell us the maximum sizes WebGPU allows this page to use. 

Output will appear here.

Step 4

Allocate GPU buffers

GPU memory 
const input = new Float32Array([1, 2, 3, 4]);
const buffer = device.createBuffer({
  size: input.byteLength,
  usage: GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_DST,
});

Buffers are chunks of GPU-accessible memory. In LLMs, model weights, activations, and KV cache are also represented as GPU buffers. 

Output will appear here.

Step 5

Run a compute shader: multiply by 2

WGSL compute 
@group(0) @binding(0) var<storage, read> input: array<f32>;
@group(0) @binding(1) var<storage, read_write> output: array<f32>;

@compute @workgroup_size(1)
fn main(@builtin(global_invocation_id) id: vec3<u32>) {
  let i = id.x;
  output[i] = input[i] * 2.0;
}

WGSL is WebGPU's shader language. Here each GPU invocation handles one number. The browser maps this GPU work to Metal, Direct3D, or Vulkan internally. 

Output will appear here.

Step 6

Vector addition

Parallel math 
output[i] = left[i] + right[i];

GPUs are good at running the same operation over many values. Vector operations like this are small cousins of model math. 

Output will appear here.

Step 7

2x2 matrix multiplication

LLM analogy 
// C = A x B
C[row, col] =
  A[row, 0] * B[0, col] +
  A[row, 1] * B[1, col];

LLMs use much larger matrix operations. This tiny version shows the shape of the same idea without hiding it behind a library. 

Output will appear here.

Step 8

CPU vs GPU wall-clock timing

Timing 
const start = performance.now();
// run CPU loop and GPU dispatch
const elapsed = performance.now() - start;

This compares browser-visible elapsed time. For tiny work, CPU can be faster because GPU setup and readback overhead dominate. GPUs shine when the work is large and parallel.

How this maps to WebLLM

This page creates tiny buffers and simple shaders. WebLLM does the same kind of orchestration at a larger scale: model weights, token data, temporary tensors, and attention cache are placed in GPU-accessible buffers, then optimized kernels run through WebGPU.

IndexedDB and WebLLM caching

IndexedDB persists across page refreshes and browser restarts until site data is cleared. In the WebLLM POC, the configured cache backend lets WebLLM keep downloaded model artifacts locally so the next load can avoid downloading the full model again.
